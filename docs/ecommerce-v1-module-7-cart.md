# Ecommerce Version 1.0 — Module 7 Cart

Status: **Authoritative**

This specification completes the recovered Module 7 architecture. It governs the
database foundation and the initial standalone Simple Product Cart slice.

## Aggregate and ownership

`Cart` is the aggregate root and the database is its source of truth. A Cart MUST
have exactly one owner: either a Customer `user_id` or a SHA-256
`guest_token_hash`. Both set and both absent are invalid. The raw guest bearer
token MUST NOT be persisted, logged, flashed, serialized, or exposed.

Version 1 permits at most one Cart per Customer and one Cart per guest-token hash.
Customer Cart identity MUST remain stable. A Customer Cart MUST NOT be reassigned
to another Customer or converted into a Guest Cart.

## Tables

### `carts`

| Column | Type | Rules |
|---|---|---|
| `id` | BIGINT UNSIGNED | Primary key |
| `user_id` | BIGINT UNSIGNED | Nullable; unique FK to `users.id` |
| `guest_token_hash` | CHAR(64) | Nullable; unique |
| `last_activity_at` | DATETIME | Required |
| `expires_at` | DATETIME | Required |
| `created_at`, `updated_at` | TIMESTAMP | Framework timestamps |

The database MUST enforce the owner XOR invariant. The `user_id` foreign key
cascades on Customer deletion because a Cart is mutable convenience state.
Indexes are required on `last_activity_at` and `expires_at` for lifecycle and
cleanup queries.

### `cart_items`

| Column | Type | Rules |
|---|---|---|
| `id` | BIGINT UNSIGNED | Primary key |
| `cart_id` | BIGINT UNSIGNED | Required FK to `carts.id` |
| `product_id` | BIGINT UNSIGNED | Required FK to `products.id` |
| `product_type` | VARCHAR(30) | Required; PHP-backed enum |
| `configuration_hash` | CHAR(64) | Required deterministic merge key |
| `quantity` | DECIMAL(15,4) | Required; greater than zero |
| `created_at`, `updated_at` | TIMESTAMP | Framework timestamps |

Deleting a Cart or its referenced convenience-state Product cascades to its
items. `(cart_id, product_id, configuration_hash)` is unique. Items are
displayed oldest first using `created_at`, then `id`; no `sort_order` exists.

`product_type` uses application-managed values `simple`, `configurable`, and
`bundle`. The initial implementation operates only on `simple`.

### `cart_item_bundle_items`

| Column | Type | Rules |
|---|---|---|
| `id` | BIGINT UNSIGNED | Primary key |
| `cart_item_id` | BIGINT UNSIGNED | Required FK to `cart_items.id` |
| `bundle_option_item_id` | BIGINT UNSIGNED | Required FK to `bundle_option_items.id` |
| `quantity` | DECIMAL(15,4) | Required; greater than zero |
| `created_at`, `updated_at` | TIMESTAMP | Framework timestamps |

This table is the authoritative normalized Bundle selection. Deleting the parent
CartItem cascades. Deleting a selected Bundle configuration row cascades that
selection; subsequent Cart validation MUST remove the now-invalid parent Bundle
CartItem and communicate the adjustment. The selected option item owns its
BundleOption and Product relationships, so those identifiers are not duplicated
here. `(cart_item_id, bundle_option_item_id)` is unique. Bundle operations are
deferred.

## Item rules

- CartItems store identifiers, configuration, and quantity only. They MUST NOT
  snapshot names, prices, tax, images, or stock.
- Prices and availability are live and MUST be recalculated from Catalog,
  Settings, Tax, and Inventory through their existing owners.
- Cart operations MUST NOT reserve or mutate Inventory.
- Public Add and Update requests accept positive integer quantities only, while
  persisted quantities remain `DECIMAL(15,4)`.
- A zero or negative internal update removes the line when that service-level
  behavior applies; an invalid positive storefront quantity is rejected.
- Simple items reference standalone Simple Products.
- Configurable items will reference the selected Simple variant, whose valid
  configurable parent must be verified. A configurable parent cannot be stored
  as the selected Product.
- Bundle items reference the Bundle parent; normalized child selections define
  their configuration.
- Identical valid configurations merge using `configuration_hash`. Different
  configurations remain separate.

## Expiration and activity

`expires_at` equals `last_activity_at` plus the configured Cart lifetime, whose
default is 30 days. Meaningful mutations—add, changed quantity, remove, clear,
and merge—MUST capture one timestamp and update both fields from it.

Viewing a Cart, rendering the navbar count, and other read-only requests MUST NOT
change activity or expiry. Expired Carts are physically deleted. Cleanup MAY run
on a schedule, while resolution MUST also treat expired Carts as absent.

## Guest token behavior

Guest bearer tokens MUST be generated by a cryptographically secure source with
at least 256 bits of entropy. Only their SHA-256 hashes are queried or stored.
Read-only requests MUST NOT create an empty Guest Cart. A token is issued only
when a guest mutation first requires a Cart. After a successful authenticated
merge, the browser token is invalidated; a future anonymous mutation receives a
new token.

## Guest-to-customer merge

Merge MUST execute in one transaction with deterministic Cart and item locking.
The existing Customer Cart is the target and its ID is preserved. Matching
configurations combine quantities up to current available stock; excess is
discarded and a clear adjustment warning is returned. Nonmatching valid items
move into the Customer Cart. The Guest Cart is deleted only after all merge work
succeeds. The guest cookie is removed only after the transaction succeeds.

When Coupons are implemented, the Customer Cart coupon wins; the Guest Cart
coupon is used only when the Customer Cart has none, and the survivor is
revalidated. No coupon column exists in the initial Cart migration.

## Checkout boundary

Checkout is deferred. Future Checkout MUST lock and revalidate the Cart, validate
pricing/configuration/coupon/shipping/stock, create the complete Order snapshots,
CouponUsage, and initial Payment obligation, then clear CartItems and provisional
state in the same database transaction. Any failure rolls back both Order and
Cart changes. Only external effects occur after commit.

## Initial Simple Product slice

Version 1 initially supports resolving guest/customer Carts, adding eligible
standalone Simple Products, viewing, updating, removing, clearing, expiration,
header quantity, and authenticated merge. Configurable and Bundle schema and
relationships are compatibility foundations only. Coupons, Checkout, Orders,
Payments, shipping calculations, and inventory reservation are outside this
slice.
